antlr-ng migration — what changed and why

Background: this branch (finish-antlr-ng-migration vs main) swaps the parser toolchain behind Neo4j's Cypher language support — Java-based ANTLR codegen + the old antlr4 runtime → antlr-ng + antlr4ng — and replaces the vendored antlr4-c3 completion fork with the published upstream package (history in 1.3). ~400 lines of product code changed, ~7k lines of vendor deleted; unit tests, the formatting corpus, and a clean build are green. Below: every non-self-explanatory change, grouped by kind, with the alternative that was (or could still be) considered.

Why it's worth doing: the old antlr4 JS runtime is effectively dormant — its last publish (4.13.2) was Aug 2024, and it lags mainline ANTLR: it never implemented exitRule's EOF handling (see 2.2). antlr4ng is a TypeScript-native rewrite that per its readme "implements everything the Java runtime does", developed as one coherent stack with antlr-ng and antlr4-c3 (releases into 2025). Its stricter, honest types are what let us delete the @ts-ignore default-export hack and the isErrorNode() workarounds (see 3.5). On performance we did not measure our own workload; upstream's public benchmark suite (MySQL grammar, monitored for regressions) shows antlr4ng beating the old antlr4 JS runtime by 9–35% — a likely indicator the switch is not a regression for us.

1. The big moves

1.1 Parser codegen: antlr4-tools (Java jar) → antlr-ng

What: gen-parser no longer downloads/runs the Java-based ANTLR 4.13.2 jar via antlr4-tools; it uses antlr-ng, a TypeScript-native port of the ANTLR generator. The CI step that curled antlr-4.13.0-complete.jar is deleted; Java and the antlr4-tools pip package are gone from CONTRIBUTING.md prerequisites.

Why: no Java/Python prerequisite for contributors or CI; the generator and the runtime (below) come from the same author and move together.

Alternative: stay on antlr4-tools + the official Java generator.

Zero migration risk, but it chains the repo to the old antlr4 JS runtime (which upstream barely maintains) and — critically — blocks unvendoring antlr4-c3, since upstream antlr4-c3 3.x is built on antlr4ng. Keeping the old toolchain means keeping the fork forever.

1.2 Runtime: antlr4@4.13.2 → antlr4ng@3.0.16

What: the parser runtime the generated code runs against. Nearly every other change in this document is a consequence of API differences between these two runtimes.

Why: antlr4ng is the runtime antlr-ng generates code for; it is actively maintained and is what upstream antlr4-c3 targets. Exact-pinned (3.0.16, not a range).

Alternative: none that keeps 1.1 and 1.3 — the three moves are one decision. The real alternative was "don't migrate", i.e. keep the old runtime + Java codegen + vendored fork as a set.

1.3 Unvendor antlr4-c3: fork in vendor/ → published antlr4-c3@3.4.4

What: the entire vendor/antlr4-c3 directory (~7k lines, including the fork's patch, upstream's test suite, and grammar fixtures) is deleted; the completion engine is now a normal dependency. The build no longer pre-builds the vendor package or copies its dist into dist/esm/vendor/.

Why it can go now: the fork addressed compatibility with the old antlr4 runtime and later gained an optional follow-up completion feature. Upstream antlr4-c3 now targets antlr4ng directly, removing the original reason to vendor it.

What the fork added: it computed follow-up token chains for every completion candidate and marked them optional, letting the completer offer both style and style reset at :. Upstream only attaches follow-ups when the caret's follow set is a single token (hasTokenSequence), so with 14 console-command candidates at :, style now gets an empty follow-up list.

Measured impact: the only product-facing loss in the suite is the combined style reset entry. The command still parses, highlights, and completes in two steps (:style → reset). A probe over ~7,300 completion positions found other merged keyword pairs, but their bare keyword remains offered and valid; no legal continuation disappears.

Decision (oskar): drop the extra feature — two-step completion is the accepted behavior going forward, not an open question. The alternatives were considered and set aside:

  • Restore without a fork: subclass CodeCompletionCore and override getFollowingTokens (~40 lines against the antlr4ng ATN) plus an "optional" flag in completionCoreCompletions.ts. Feasible, but re-commits us to maintaining fork-only behavior indefinitely.
  • Keep the fork: re-port the patch onto antlr4-c3 3.4.4 and keep vendoring. Highest fidelity, highest maintenance — defeats the purpose of the migration.
  • Propose upstream: PR the optionals feature to antlr4-c3. Clean end state, slowest, not in our control.

1.4 Dependency hygiene: one runtime copy only

What: antlr4-c3@3.4.4 exact-pins antlr4ng@3.0.16 — the same copy language-support depends on, so there is no dual-runtime instanceof hazard. The antlr4ng@3.0.15 in the lockfile comes from stringtemplate4ts (used by antlr-ng at codegen time only, never at runtime). antlr4@4.13.2 survives only via lint-worker's deliberate pin of old published language-support versions (needed to lint against older Neo4j versions).

Alternative: none needed — but worth guarding: a renovate rule now disables automatic bumps of antlr4ng/antlr4-c3/antlr-ng, since antlr4ng must move in lockstep with antlr4-c3's internal pin (two runtime copies would break instanceof checks everywhere).

2. Semantic adaptations (where behavior could have changed)

2.1 ErrorTrackingStrategy replaces ctx.exception

What changed: the old runtime attached each parser exception to the rule context that caught it:

catch (re) {
    if (re instanceof RecognitionException) {
        _localctx.exception = re;
        this._errHandler.reportError(this, re);
        this._errHandler.recover(this, re);
    } else { throw re; }
}

antlr4ng removed ctx.exception. Recording in SyntaxErrorsListener is not equivalent: DefaultErrorStrategy suppresses listener notifications while recovering, whereas generated catch blocks always call reportError. ErrorTrackingStrategy therefore overrides that public hook, records recognizer.context → exception, then delegates to the default strategy. Recovery behavior remains inherited and unchanged. Cypher has no left-recursive generated rules, so recognizer.context is the context whose catch block fired.

Who consumes it: four old sites, in two shapes:

  • "Was this pattern element valid?" — child.exception === null → !errorTracker.hasError(child): schemaBasedCompletions.ts (×2 — finding the last valid node/relationship pattern so label/rel-type completion still works after a broken segment) and the snippet path in completionCoreCompletions.ts. Purely boolean checks.
  • "Where did parsing break?" — formatting's getParseTreeAndTokens used tree.exception.offendingToken to locate unparsable input and format around it; now errorTracker.offendingTokenAt(tree).

The tracker is fresh per statement parse and is exposed on ParsedStatement.errorTracker; formatting creates its own.

Nuances & impact:

  • First vs. last: the old runtime overwrote _localctx.exception on each catch, so tree.exception was the last exception a context caught; our Map is insert-if-absent, so we keep the first. Irrelevant for the boolean checks; for formatting's offending-token lookup, "first error on the root context" is arguably the better answer to "where does the broken region start" — and the 11,933-query formatting corpus shows no divergence either way.
  • Cost and API: one Map insert per caught error; ParsedStatement gains a required field, but no downstream code constructs it manually.

Alternatives considered:

  • Post-hoc tree walk for ErrorNode children — different semantics: an error node under a context is not the same as "this rule's catch fired", and it would force every consumer to re-walk.
  • Match old last-wins semantics — a one-word change (drop the insert-if-absent guard) if we ever want bit-exact fidelity; first-wins reads better for the formatting use case.

2.2 parseToCommand: EOF stop via CommonTokenStream.LB

Before this PR: parseToCommand extracts each statement's original text with inputStream.getTextFromRange(stmtStart.start, stop.stop), where stop came from the root rule context. The old antlr4@4.13.2 JS runtime always assigned LT(-1) when leaving a rule, so after matching EOF the context happened to stop on the last real default-channel token. The extraction code relied on that behavior without needing to say so.

After this PR: antlr4ng follows mainline ANTLR and records the matched EOF token as the root context's stop. After the rule returns, the CommonTokenStream cursor is still positioned on EOF, so tokenStream.LB(1) retrieves the preceding on-channel token through antlr4ng's public API. CommonTokenStream defines LB as channel-aware, meaning whitespace and comments on the hidden channel are skipped automatically. Empty input returns null and retains EOF; a semicolon result continues through the pre-existing semicolon adjustment.

This matches the Java runtime's Parser.exitRule; the old JS runtime was the outlier. The migration makes that dependency explicit using the new runtime's intended token-stream API. For example, RETURN 1 // note still extracts as RETURN 1, because LB(1) skips the hidden space and comment. The same call works for both the real final EOF and the per-statement EOF fabricated by ListTokenSource.

Who feels it: the extracted cmd.statement is what wrappedSemanticAnalysis receives per statement (syntaxValidation.ts:462) — an over-long extraction would hand Neo4j's semantic analyzer trailing comments or, worse, text past the statement boundary, shifting its diagnostics. The corrected stop also flows into ParsedCommand's position tokens used for statement-at-caret mapping. Covered by the console-commands suite (multi-statement, trailing-comment, and empty-input cases) and the semantic-validation suite.

2.3 Statement splitting: ListTokenSource — no internals

Why we touch tokens at all: splitIntoStatements lexes the whole file once (tokenStream.fill()), splits the token array at SEMICOLON/EOF boundaries, and clones each token through antlr4ng's public CommonToken.fromToken factory. Each clone gets a statement-local index while preserving its original character offsets and input source — the property 2.2's text extraction relies on.

What: in the old runtime the stream's tokens field was public; antlr4ng makes it protected and offers no setter. The replacement is fully public API: antlr4ng ships ListTokenSource, a TokenSource wrapper around a token array, so each chunk simply gets new CommonTokenStream(new ListTokenSource(chunk)). No lexer is involved when a statement stream is parsed anymore (previously all statement streams shared one lexer as a fallback token source).

Separation of responsibilities: the splitter now returns only Token[][]. Parsing callers wrap each chunk in ListTokenSource and CommonTokenStream when they actually need a parser; lexer-only callers consume the arrays directly. This keeps tokenization/splitting separate from parser construction and avoids carrying a stream and its backing array as duplicate state.

One behavioral nuance: for a semicolon-terminated (non-final) statement the parser previously over-read into the shared lexer's whole-file EOF; it now gets an EOF fabricated by ListTokenSource, positioned at the end of the chunk. The LB(1) lookup in 2.2 returns the token before either kind of EOF, so statement extraction is identical; error diagnostics for a broken mid-file statement now point at the statement's end (e.g. the ; in MATCH (n; RETURN 1) rather than at end of input — arguably the better position. Covered by the console-commands and semantic-validation suites.

Alternatives considered:

  • Re-lex each statement chunk with a fresh lexer over the statement text — also public API, but re-tokenizes (slower) and produces different token objects/indices than the whole-file pass.
  • Read and write the protected tokens field via typed casts — works, but depends on antlr4ng internals; ListTokenSource achieves the same through public API.

2.4 parseStatementsStrs: split without parsing

What: it used to fully parse every statement — full parser run with error strategy and all collector listeners attached — just to return the statement strings. Now it calls the pure lexer-level getStatementTokenChunks helper and joins each chunk's token text. It neither runs nor constructs a parser, and does not create per-statement token streams. Same output, strictly less work.

Why the old version parsed at all: it simply reused parse(), but statement boundaries are a lexer-level question (semicolons outside strings/comments), so the parse was overkill from the start — the rewrite fell out naturally from the scaffolding refactor.

Cross-check with Neo4j's cypher-shell: cypher-shell makes the same architectural choice in ShellStatementParser.readCypher: it scans input while tracking quote and comment delimiters, and ends a statement only on a semicolon outside those regions; it does not invoke the Cypher parser to find boundaries. This implementation delegates the delimiter state machine to the generated lexer instead of maintaining a second handwritten Cypher-aware scanner. The output contracts remain intentionally different: cypher-shell strips leading whitespace/comments and the terminating semicolon and records whether a statement was complete, while parseStatementsStrs preserves the existing source chunks used by the VS Code execution path.

Who calls it: the VS Code extension's cypherRunner.ts — the "run query" path splits the editor text into statements to execute them one by one. So this is a user-facing path, and it now skips a full parse per run. Output equivalence is covered by the existing unit tests.

Alternative: keep the parse-based version — works, but pays a full parse per statement for a lexer-level question.

2.5 Remove the antlrUtils compatibility wrapper

What: antlrUtils.tree.Trees is gone. The language-support package now re-exports antlr4ng's named Trees value and ParseTree type directly, and the CodeMirror playground uses those upstream APIs.

Why the wrapper existed: it was glue code from the start. The old antlr4 runtime exposed Trees only through an untyped default-export shape, so the repo used @ts-ignore, a hand-written nested interface, and a double cast merely to make two tree helper calls. It was introduced for the playground's parse-tree viewer rather than as a designed language-support abstraction. The declared interface was also misleading: getChildren was typed as returning only ParserRuleContext[], even though parse trees also contain terminal nodes.

Why removal is better now: antlr4ng exports Trees and ParseTree as first-class, typed symbols. Re-exporting them keeps consumers on the same runtime copy as the generated parser while removing the fake antlr4 namespace, the ignored type error, the unused third parser argument to getNodeText, and the incorrect rule-context-only child type. The playground now walks the honest ParseTree union, including terminal nodes.

Compatibility check: the only in-repo/upstream consumer was the CodeMirror playground. A search of the adjacent ~/work/upx monorepo found no use, and public GitHub searches found no other Neo4j or external consumer. The symbol was publicly exported, so an unknown private consumer cannot be ruled out, but it was undocumented and the available evidence says the removal is low risk.

Alternative considered: retain antlrUtils as a deprecated adapter. That would preserve the old import name, but also keep a repo-specific API shape whose only known consumer has already moved to the upstream API. Removing it makes the migration's end state smaller and clearer.

3. Mechanical renames (no behavior change)

3.1 Default exports → named exports

What: antlr-ng generates named exports only, so import CypherLexer from … became import { CypherCmdLexer as CypherLexer } from … throughout. index.ts keeps the public names (CypherLexer, CypherParser, CypherParserListener, CypherParserVisitor) via aliases, so downstream packages are untouched.

3.2 List accessors: ctx.expression_list() → ctx.expression()

What: antlr-ng names repeated-rule accessors after the rule (overloaded: ctx.expression() returns all, ctx.expression(i) returns one); same for token lists (COMMA_list() → COMMA()). This is the bulk of the formatting.ts diff — dozens of call sites, all mechanical, verified by the full 11,933-query formatting integrity corpus.

3.3 Context/plumbing renames

  • ctx.parentCtx → ctx.parent
  • parser._ctx → parser.context (also removes a @ts-expect-error on ruleIndex)
  • parser._parseListeners = […] → removeParseListeners() + one addParseListener() per listener (antlr4ng encapsulates the list)
  • CharStreams.fromString → CharStream.fromString
  • inputStream.getText(start, stop) → getTextFromRange(start, stop)
  • tokenStream.tokens reads → public getTokens(), or the chunk arrays handed back directly by splitIntoStatements (see 2.3)
  • VariableCollector now receives the CommonTokenStream via constructor instead of reaching through ctx.parser.getTokenStream()

3.4 Listeners: extends ParseTreeListener → implements

What: in antlr4ng ParseTreeListener is a pure interface, so the collector classes implement it with explicit no-op methods (enterEveryRule, visitTerminal, visitErrorNode) instead of inheriting them.

3.5 isErrorNode() hack → instanceof ErrorNode

What: the old runtime had no real ErrorNode class in its types, so formatting did a @ts-expect-error + runtime node.isErrorNode() dance. antlr4ng has the class, so both sites are now plain instanceof checks — strictly cleaner.

3.6 Error-listener signature update

What: SyntaxErrorsListener.syntaxError now matches antlr4ng's signature: offendingSymbol may be null and two extra parameters (msg, e) arrive. A null-guard on offendingSymbol was added — the only behavioral delta, and a defensive one.

syntaxValidationHelpers.ts

3.7 Grammar action: this.getModeStack() → this.modeStack

What: the embedded lexer action in CypherCmdLexer.g4 (the RCURLY override that makes interpolated strings lex correctly). antlr4ng exposes modeStack as a getter property; there is no getModeStack() method, so the old form would not compile. Not a gratuitous hand edit.

Clobber risk: none — the monthly artifact bot only overwrites Cypher25Lexer/Parser.g4, semanticAnalysis.js and the lint-worker version tag; CypherCmd*.g4 are repo-local (now stated explicitly in AGENTS.md, and the .g4 comment names antlr4ng).

4. Build, CI & deleted files

4.1 Deleted: vendor/antlr4-c3 and its tests

What: ~7k lines: the forked completion core, its build config, and two test suites — CodeCompletionCore.spec.ts (13 cases, upstream's own engine suite run against the fork; that coverage now lives in upstream antlr4-c3's CI) and CodeCompletionOptionals.spec.ts (8 cases testing the fork-only feature, plus its Optionals.g4 fixture — moot now that the feature is dropped, see 1.3). No product test was deleted; the only expectation change in packages/ is the style reset entry (1.3) plus pure API renames in lexer.test.ts.

  • pnpm-workspace.yaml: dropped vendor/*

  • knip.json: dropped the vendor ignore and the antlr4 binary ignore

  • packages/language-support/tsconfig.json: include no longer reaches into the vendor dist

4.3 language-support moves to moduleResolution nodenext

What: language-support now uses module/moduleResolution: "nodenext", so TypeScript enforces .js on relative imports. The apparent blocker was not antlr4's legacy declarations but our own direct antlr4 type imports; after migration, the remaining legacy dependency is covered by skipLibCheck. The conflicting --module esnext build overrides were removed, and a rebuild verified unchanged ESM output apart from intended source edits.

Scope: check-imports no longer scans language-support. Query-tools and lint-worker retain it because they are not "type": "module" and have different CJS/ESM bundling constraints.
